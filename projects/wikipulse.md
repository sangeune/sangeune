## 프로젝트 개요

위키백과에서 사람이 편집하고 조회수까지 급증한 문서를 찾아 사건 단위로 묶고, 관련 미국 상장 종목 정보와 함께 보여주는 서비스입니다.
같은 판정·클러스터링 코드를 실시간 스트림(LIVE)과 과거 데이터 재생(replay)에 함께 사용합니다.

| 단계 | 팀 전체 구성 | 내 담당 |
|---|---|---|
| 수집 | 실시간 EventStreams → Kafka, 과거 편집 덤프 | **과거 편집 덤프 적재·정규화** |
| 판정 | Spark Streaming, 편집·조회수 2단계 관문 | **판정 결과 저장, 실시간·과거 출처 분리** |
| 묶음 | 시점별 상위 문서 선택 → 링크 기반 클러스터링 | **클러스터링 v2 프로덕션 구현** |
| 매칭 | GDELT 뉴스, 종목 후보, LLM 검증 | — |
| 서빙 | Spring Boot API, React 화면 | 펄스맵 렌더 버그 수정, 한국어 표시 제목 |

**제가 하지 않은 것**: 급증 판정 수식과 28일 기준선 설계, Kafka·Spark·HDFS 인프라 구축, CI/CD, 뉴스·LLM 기반 종목 매칭은 다른 팀원이 담당했습니다.

## 내가 담당한 작업

### 1. 클러스터링 v2 프로덕션 반영

- **문제**: 급증 문서를 서로의 링크로 묶으면 그날 뜬 문서가 하나로 이어진 거대 클러스터가 생겼습니다. 관련 없는 사건이 한 이슈로 합쳐져 화면에 보였습니다.
- **한 일**: PoC에서 검증한 2단계 규칙을 실제 파이프라인 코드로 옮겼습니다.
  - 시점마다 조회수 상위 20개 문서만 고르는 단계(`root_selection.py`, 24시간 쿨다운)
  - 그 안에서 링크로 연결된 문서끼리 묶고 허브 문서를 억제하는 단계(`rootgraph.py`)
  - 판정 시점 판본의 원문 링크만 가져오는 수집기(`asof_links.py`). 현재 판 기준 링크를 쓰면 나중에 추가된 링크가 섞이는 미래 정보 누수가 생겨, 과거 판본의 wikitext 링크만 사용했습니다.
  - 클러스터를 다시 저장할 때 뒤 단계 산출물이 함께 지워지지 않도록 삭제 가드를 넣고, PoC 결과와 비교하는 회귀 도구를 만들었습니다.
- **결과** (같은 2개월 과거 재생, 같은 링크 묶음 규칙, 1,104개 시점):

| 구성 | 20개 이상 문서 거대 클러스터 | 최대 클러스터 크기 |
|---|---:|---:|
| 상위 문서 선택 없이 급증 문서 전체(162,775건)를 묶을 때 | 59개 | 63 |
| 상위 문서 선택 적용 (22,080건) | **0개** | **16** |

  - 프로덕션 코드의 상위 문서 선택 결과가 PoC 결과와 22,080건 모두 일치했습니다.
- **한계**: 문서 1개짜리 클러스터가 90.4%(17,569/19,432)입니다. 잘못 묶는 것을 막는 대신 덜 묶는 쪽을 택한 결과이며, 저장소 문서에 한계로 기록했습니다.

### 2. 결과가 바뀌지 않는다는 것을 먼저 증명한 사전필터

- **문제**: 60일 과거 데이터를 실시간과 같은 로직으로 연속 재생할 때, 모든 구간마다 DB에서 기준선을 읽으면 느렸습니다. 거르다가 진짜 급증을 놓칠 위험도 있었습니다.
- **한 일**: 판정 코드의 모든 통과 경로가 공통으로 넘어야 하는 최소 조건만으로 거르는 사전필터를 설계하고, 연속 재생 진입점(`bulk_replay.py`)을 작성했습니다. 임계값은 판정 코드와 같은 상수를 참조하게 했습니다.
- **검증** (당시 판정 규칙 기준의 합성·테스트 입력):
  - 경계값 격자 1,960개 조합(급증 672건): 유실 0, 판정 결과 불일치 0
  - 난수 20,000개 구간: 급증 목록 완전 일치
  - 조건을 일부러 한 칸 바꾸면 72건 유실을 테스트가 잡아내는지 확인(변이 테스트)
- **참고**: 이때 만든 재생 데이터셋은 이후 팀 판정 규칙이 바뀌면서 판정 검증용으로는 폐기 표시되었습니다. 사전필터 함수 본문도 새 규칙에 맞춰 팀원이 다시 작성했고, 테스트 구조는 유지되었습니다.

### 3. 판정 결과 저장과 실시간·과거 결과 출처 분리

- 판정 결과를 PostgreSQL에 저장하는 런타임과 저장 계층을 작성했습니다. 감지 시각을 실행 시각이 아닌 구간 끝 시각으로 고정해 재실행해도 값이 같도록 했습니다.
- 마이그레이션 `V5__spike_source.sql`에서 고유 키에 출처(`live`/`replay`)를 넣고 허용 값 제약을 걸었습니다. 기존 행을 채운 뒤 기본값을 제거해, 출처를 빠뜨린 코드가 조용히 과거 데이터로 저장되지 않게 했습니다.
- 클러스터 입력을 출처로 거르고 `--source`를 필수 인자로 바꿨습니다. 통제 입력(과거 48건, 실시간 2건)으로 교차 혼입 0건을 확인했습니다.

### 4. 과거 데이터 적재와 정규화

- 위키백과 `mediawiki_history` 덤프를 실시간 이벤트와 같은 형식으로 변환하는 적재 CLI를 작성했습니다(스키마, 정규화, 이어받기, manifest).
- 로컬 측정: enwiki 2025-06 덤프 5,501,827행 → 3,361,013 이벤트, 파싱 오류 0건
- 문서 제목 표기 규칙(공백·밑줄·유니코드 정규화)을 정하고 세 개 경로에 같은 규칙을 적용했습니다.
- 과거 재생이 그 시점에 공개되지 않은 데이터를 쓰지 않도록, 문서 생성 시각 인덱스(`page_creation.py`)를 만들고 월 선택 규칙을 팀 규칙 하나로 통합했습니다.
